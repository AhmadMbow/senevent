Lab 7 — Workspace npm + packages/shared

Rapport de réalisation : un refactoring sans nouvelle fonctionnalité. Le projet devient un monorepo npm workspaces. Toute la logique Supabase — client, requêtes, formes de données — quitte les composants React pour packages/shared, écrite une seule fois en TypeScript. Le web l'importe via @senevent/shared ; le mobile en fera autant. Le test de réussite : l'app se comporte exactement comme avant.

01 Le problème : une logique, bientôt deux clients

L'app web est finie et marche. Mais chaque requête Supabase est écrite en dur dans un composant : lib/supabase.js pour le client, .from().select() dans App.jsx, .insert() dans NouvelEvenement.jsx… Aux Labs 8–10, le mobile aura besoin d'exactement la même logique. La laisser ici, c'est se condamner à la réécrire — deux copies qui divergeront. Le monorepo résout ça : un seul dépôt, un dossier partagé, importé par les deux apps.

Avant — tout dans apps/web

02 La racine qui déclare les workspaces

Un package.json à la racine transforme le dépôt en monorepo. "workspaces" dit à npm où chercher les sous-projets ; "private": true empêche une publication accidentelle de la racine. Un seul npm install installe tout et crée un lien symbolique de @senevent/shared dans les node_modules — le web importe alors le package local, sans passer par le registre public.

package.json (racine)

{
  "name": "senevent",
  "private": true,
  "version": "1.0.0",
  "workspaces": ["apps/*", "packages/*"]
}

packages/shared/package.json

{
  "name": "@senevent/shared",
  "version": "1.0.0",
  "type": "module",
  "main": "src/index.ts",
  "types": "src/index.ts",
  "dependencies": {
    "@supabase/supabase-js": "^2.0.0"
  }
}

Le scope @senevent/ est un espace de nommage : il signale un paquet interne et évite les collisions. "main" pointe vers src/index.ts, la façade que les apps obtiennent en important le nom.

03 TypeScript, là où il apporte le plus

Six labs en JavaScript pur, volontairement. Maintenant que React est acquis, TypeScript entre au bon endroit : le code partagé, qui décrit des données. Un événement a un titre (texte), un prix (nombre), une catégorie (parmi 5 valeurs). On déclare ces formes une fois, et l'éditeur attrape ev.titr, un texte passé pour un nombre, ou un champ obligatoire oublié — avant l'exécution.

packages/shared/src/types.ts

export type Categorie =
  | "concert" | "expo" | "conference" | "atelier" | "soutenance";

export interface Evenement {
  id: number;
  titre: string;
  categorie: Categorie;         // pas n'importe quel texte : 5 valeurs
  lieu_nom: string;
  date_debut: string;           // ISO 8601
  prix: number;
  image_url: string | null;     // le | null force a gerer "pas d'image"
  organisateur_id: string | null;
  created_at: string;
}

export interface NouvelEvenementInput {
  titre: string; categorie: Categorie; lieu_nom: string;
  date_debut: string; prix: number;
  image_url?: string | null;    // optionnel a la creation
  organisateur_id: string;      // obligatoire : RLS l'exige
}

Le | null n'est pas décoratif

Sur image_url et organisateur_id, il force le code à gérer le cas « pas d'image » ou « pas d'organisateur » — précisément les 5 événements seed, dont profiles vaut null. Sans ce marqueur, on oublierait ce cas et l'interface planterait sur un undefined. Le mode strict du tsconfig.json rend cette vérification obligatoire.

04 Le client découplé : pourquoi initSupabase

Le package ne peut pas lire import.meta.env.VITE_... : cette syntaxe est propre à Vite, et Expo lit ses variables autrement. La solution : le package ne lit rien lui-même. Chaque app lui passe l'URL et la clé au démarrage via initSupabase(url, key). Le package reste agnostique — c'est ce découplage qui fera marcher le même code côté web et côté mobile, sans modification.

packages/shared/src/supabaseClient.ts

let client: SupabaseClient | null = null;

// L'application passe ses cles au demarrage. Le package ne lit
// JAMAIS import.meta.env : ni Vite, ni Expo, agnostique.
export function initSupabase(url: string, anonKey: string) {
  if (!client) client = createClient(url, anonKey);
  return client;
}

export function getSupabase(): SupabaseClient {
  if (!client) throw new Error("Supabase non initialise.");
  return client;
}

apps/web/src/main.jsx

import { initSupabase } from "@senevent/shared";

// C'est ici, et SEULEMENT ici, qu'on lit import.meta.env.VITE_...
initSupabase(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
);

createRoot(document.getElementById("root")).render(
  <StrictMode><App /></StrictMode>
);

Résultat : main.jsx est le seul fichier de tout le projet qui lit les variables d'environnement. Partout ailleurs — composants comme package — on ne connaît que getSupabase().

05 Un contrat d'erreur unifié : throw plutôt que retourner

Au Lab 6, chaque appel renvoyait { data, error } et le composant testait error ligne après ligne. Les fonctions partagées lèvent l'erreur : le composant appelant veut juste la donnée. On centralise la décision dans le package, et les deux apps gèrent tout de la même façon avec un try / catch.

Avant — { data, error } dans le composant

// Lab 6 — dans le composant : verifier error a chaque appel
const { data, error } = await supabase
  .from("evenements")
  .select("*, profiles(nom)")
  .order("date_debut", { ascending: true });
if (error) {
  setErreur(error.message);
} else {
  setEvenements(data);
}

Après — la fonction partagée lève

// Lab 7 — la fonction partagee leve, le composant fait try/catch
export async function getEvenements(): Promise<Evenement[]> {
  const { data, error } = await getSupabase()
    .from("evenements")
    .select("*, profiles(nom)")
    .order("date_debut", { ascending: true });
  if (error) throw error;          // decision centralisee
  return (data ?? []) as Evenement[];
}

06 Brancher apps/web : des appels aux imports

Composant par composant, on remplace les appels Supabase en dur par un import du package. Le composant ne sait plus comment on récupère les événements — juste qu'il appelle une fonction qui les retourne.

Avant — App.jsx (Lab 6)

import { supabase } from "./lib/supabase";

const charger = async () => {
  setChargement(true);
  setErreur(null);
  const { data, error } = await supabase
    .from("evenements")
    .select("*, profiles(nom)")
    .order("date_debut", { ascending: true });
  if (error) setErreur(error.message);
  else setEvenements(data);
  setChargement(false);
};

Après — App.jsx (Lab 7)

import { getEvenements } from "@senevent/shared";

const charger = async () => {
  setChargement(true);
  setErreur(null);
  try {
    const data = await getEvenements();   // toute la requete est dans le package
    setEvenements(data);
  } catch (e) {
    setErreur(e.message);
  } finally {
    setChargement(false);
  }
};
